# Visibility and sharing

## Profile links

Login is required for all profiles, journals, per-user statistics, and every send beyond a signed-out climb page's anonymized latest 10. The one profile exception is the owner's share link, `/users/{id}?share=<token>`: while its token in `profile_share_links` is current and the profile isn't private, a signed-out holder sees the owner's name, avatar, hardest sends, send count and latest `SHARED_PROFILE_SENDS` sends, with commentary only where it is shared with Everyone (`get_share_link_owner`, then the same `get_sends_for_user_page` predicate as a null viewer). Shared pages use the same components and layout as the signed-in profile. `SharedProfileHeader` renders the same heading and tabs, with a sign-up invite instead of the friend button, and only the tab the link can open, Sends. The profile link opens no trips: each trip has its own link (see [Trips](trips.md#share-links)).

Journals, trips, projects, analytics, friends and the rest of the history require sign-in, and the link preview shows only the name. The link description in `ShareProfileControls` must list everything these pages show, so update it before adding anything to them. Resetting the link or making the profile private rotates the token in SQL, so earlier links and QR codes stay dead after the profile is public again. An account created from a current link records its owner in `user.referred_by` and, once verified, sends that owner a pending friend request unless their profile is private at that moment (`welcome_new_account_once`).

## Catalog and journal audiences

Public catalog reads expose area/subarea/route names and hierarchy, area and route descriptions, route grades and disciplines, and each climb's whole-catalog send aggregates (average rating and logged-ascent count). Climb lists may therefore filter and order on any of those, including rating and ascent count; area lists have none of the climb columns and reject them. Signed-out climb pages also list the latest 10 sends through `get_public_sends_for_climb`, anonymous with a month-only date and no commentary unless the climber shares send commentary with Everyone from a public profile, and the climb's newest send videos through `get_climb_videos` with a null viewer, which applies that same Everyone rule. Every other send read and the average suggested grade require a session, except the owner's share-link preview and the [project share page](#project-links). Member APIs and page metadata authorize before reading protected data. Locked pages show Sign in/Sign up callouts. Keep authorization at the query and HTTP boundaries.

The stored `public` audience is displayed as Members (signed-in Betabook users); `everyone`, offered only for send commentary, also reaches signed-out visitors and names the climber on public send rows. The Worker checks profile privacy before loading a member page. [Profile header authorization](../../backend/worker/src/routes/member_pages.rs) Journal queries take owner/viewer IDs and read current permissions in SQL; do not pass cached privacy snapshots. A private profile is visible only to its owner, but climb send lists keep its sends as anonymous rows with no user ID, name, commentary, or exact date, keyed by negative list position rather than the sequential send ID. Journal and goals audiences are Only me, Friends, and Members; the same permission governs finished goals in friends’ activity feeds.

Friends requires an accepted mutual relationship in `friendships`; pending requests grant no access. Use `can_read_journal` for current page/metadata authorization and the same `journal_visible_sql` predicate inside data reads so stale props cannot bypass removal.

New accounts default to Members commentary and Friends journal entries and trips; member-visible send facts retain profile visibility; per-climb aggregates are public.

## Climb lists

Climb lists have the same three audiences in one setting, `user.climb_list_visibility` (default Friends), that `climb_lists_visible_sql` applies to every list read and to the profile's Lists tab. Each list may also have its own link, `/lists/{token}` in `climb_list_share_links`, which opens that one list whatever the setting says and shows its name, description, climbs and grades, and the owner's name; `CLIMB_LIST_SHARE_SENTENCE` must list everything that page shows. Client components on that page get the token, never the list id. A list's sent state and sent filter are the reader's own `sends`, never the owner's. Copying is a snapshot: `climb_lists::copy` rechecks the setting or a live token inside the write and keeps no link to the source.

## Companion tags

Companion tags follow the tagging author's audience, not the companion's: `companions_json_sql` names a tagged friend to every reader of the entry, regardless of the companion's journal audience, hiding a tag only after self-removal or an ended friendship. A private profile is deliberately not an opt-out here: it governs the profile page, which authorizes its own viewer, so the name is shown and linked to any reader of the entry, and a signed-in reader can learn a private climber's name this way just as a friend request already reveals a private requester's. Privacy is therefore never an eligibility question when tagging: `search_companion_friends` and `journal_companions_insert_guard` weigh only an accepted friendship and the ten-tag cap. Keep guard conditions to facts that cannot change after tagging: re-saving an entry re-sends its unchanged tags, and BEFORE INSERT runs even where ON CONFLICT DO NOTHING makes the row a no-op, so anything else aborts the author's next save.

## Send commentary and videos

Send commentary has an independent audience enforced by `send_comment_visible_sql`, including mirrored ascent notes and retained notes after deleting or merging sends. A send's videos are part of its commentary: `sends.videos` holds up to five canonical YouTube or Instagram links as a JSON array (`frontend/src/lib/send-video.ts`; migration 0052's triggers reject any other shape, host or character), and every read selects it under the same `send_comment_visible_sql` as the note beside it — climb and public send rows, the Sends tab and share-link profile, the feed, the ascent entry in the journal, and `get_climb_videos` (one row per video) for a climb page's video row — so they never reach an anonymous row or a private profile's viewers. Only an ascent entry carries them; repeats and sessions have no send of their own.

Rendering re-parses each stored link with `readSendVideo` and builds player URLs from the extracted id alone, and nothing is requested from YouTube but a poster (sent without a referrer) until the viewer presses play. Instagram lets no other site show the cover of a reel, so where the feed shows the one Instagram video of a send in place it loads the Instagram player with the page. In list rows, rows of several videos and the video row of a climb, Instagram is requested only after a press.

Forms send the list with a `videosChanged` marker, so a form without one leaves the stored videos alone. Project share pages don't show videos: their consent copy predates them, so adding them there changes the copy first. A trip link shows videos with the rest of the commentary it overrides.

## Project links

Exports are owner-only, and so is the Projects tab, with one deliberate exception: a project share link. `project_share_links` (migration 0048) holds one row per pinned project, keyed by a `lower(hex(randomblob(16)))` token that is the whole of `/projects/{token}` — no user or climb id is in the URL. It carries no audience on purpose: a link cannot enforce who holds it, and labelling one Friends or Members would borrow the journal audience's words for something that does not mean the same thing, inviting a climber to treat a forwardable URL as a feed setting. Anyone holding a live token can read it, signed in or not.

What can revoke it is in the `READABLE` predicate in `backend/db/src/projects.rs`, applied inside every read: `expires_at`, written by `datetime('now', …)` in SQL or null for indefinite, and the owner not being private. `shared_project` resolves a token to a status and the project in one read, and neither it nor the session read takes a viewer at all, so there is no audience check to get wrong; it selects the owner's name to tell an expiry from a closed profile, and the session query reapplies the predicate. Worker metadata runs the same predicate as the page, so a dead or expired link previews as nothing rather than naming the climber to a channel it was pasted into.

A share deliberately overrides the owner's own audiences for that one climb — both `journal_visibility` and `send_comment_visibility` — and that is the feature: the page shows the project as the owner's own board shows it, including send commentary, ascent entries, journal entry ids, and the send with its exact date, rating, suggested grade, grade feel and comment. The shared session query therefore matches the project board's aggregate exactly, so a project cannot report one session count on the owner's card and another on the page that card links to. The consent this rests on is the share dialog's "Anyone with the link sees your sessions, notes and send", said before a link exists and shaped like the profile share control's one-line description; anything added to `SharedProject` has to stay inside what those three words already cover, or the copy changes first.

One thing does not travel: companion tags, because they name third parties who did not agree to the link and who never saw the dialog. The owner's email stays out too; their user id does not, since the page links their profile, which a live link already implies is public. The composite foreign key to `pinned_projects` means a link cannot outlive its pin: untracking, deleting the climb and deleting the account all revoke it, `apply_merge.sql` moves the row to the surviving climb with its token so a merge does not silently break a link, and a trigger deletes every row when a profile goes private, so links shared beforehand stay dead once it is public again. `share_project` enforces the pin and the private check inside the INSERT rather than before it, since a session carries no `is_private` and a check in TypeScript would leave a window for a link written just after the profile closed; it returns the deadline the database computed so the dialog reports when the link actually dies.

## Friendships and avatars

A friend request reveals the requester's name/avatar to its recipient's private Friends list, even for a private requester; it grants no access to that person's private profile or history. Both participants can see an accepted connection; either can remove it. Climber suggestions (`get_climber_suggestions`) are friends of accepted friends: a private profile is never suggested and never lends its connections, anyone with a pending request either way is excluded, and a suggestion shows how many friends are shared but not who, though a viewer with few friends can infer them.

An uploaded profile photo is the one data route without a session: `GET /api/avatars/<key>` serves the object to anyone holding the URL, because the same avatar has to render in feeds, friends lists and signed-out share-link previews, and because the Google photo URL it replaces was already public on Google's CDN. New uploads use a fresh random object key. An identical upload can reuse the current photo, including an existing content-addressed photo. D1 atomically returns the image displaced by each replacement or removal so cleanup deletes only the retired object. Cached copies may remain available for the seven-day avatar cache lifetime.
