# Climbs, sends and journal entries

## Grade storage and display

`climbs.grade`, `sends.suggested_grade` and `goals.grade` are native ordinals into `BOULDER_HUECO`/`ROPE_YDS` in `frontend/src/lib/grades.ts`, whatever a climber chooses to read. `user.boulder_grade_scale`/`rope_grade_scale` (`frontend/src/lib/grade-preferences.ts`) only change labels and pickers: Rust formats grades with `GradePreferences` in `backend/domain/src/grades.rs`, and React components use `useGradePreferences` and `GradeLabel`. Where Font or French prints two ordinals alike, a picker submits the larger ordinal (`gradeOptions`) and `parseGrade` resolves text the same way. SEO, exports, moderation summaries and demo fixtures stay native. Every climb has a listed grade and every send a suggested grade: climb creation, moderation edits and `validate_send_input` require them, a new imported send or a climb break's repeat-only send without one takes the climb's listed grade, and an import overwrite with no usable grade keeps the send's current one. Migration 0054 is the backstop: `climbs_require_grade_*` rejects a null grade, and `sends_fill_suggested_grade_*` fills a null suggested grade from the climb rather than aborting, so a worker deployed before it keeps working. Both columns remain nullable in SQLite. Rebuilding `climbs` solely to add `NOT NULL` can cascade deletes, so preserve the trigger constraints.

## Ascent styles

Boulder sends are `redpoint` or `flash` only; `onsight` is a rope-only style. `ascentStylesFor` in `frontend/src/lib/sends.ts` drives the pickers and `validate_send_input`, imports coerce a boulder onsight to flash, and the `sends_reject_boulder_onsight_*` triggers from migration 0042 are the backstop. Analytics show flashes and onsights as separate stat cards and as two lines on one rate-by-grade chart; `cardAppliesTo` in `frontend/src/lib/analytics-layout.ts` leaves the onsight card out of bouldering, and the chart draws the flash line alone there.

## Sends and repeats

`sends` has one row per user/climb, including undated sends. `journal_entries` records climb sessions and training; `isAscent` distinguishes the original dated ascent from repeats. The original ascent mirrors the send's date and comment, while repeats do not add another send or rating. Keep writes consistent through atomic D1 batches in `backend/db/src/journal.rs` and `backend/db/src/sends.rs`. Check the SQL guards and `backend/db/tests/migrations_and_queries.rs` when changing logging, imports, or merges.

## Moderation

Signed-in users can create areas/climbs and edit descriptions immediately. Names, climb discipline/grade, deletion, moves, reparenting, merges, and broken-climb reports use `backend/worker/src/routes/moderation.rs` and `backend/db/src/moderation/mod.rs`. Admin role alone is insufficient: grants in `admin_area_scopes` cover subtrees, and operations spanning areas need coverage for every affected area. Preserve scope checks, self-review restrictions, and validation at application time.

## Broken climbs

A `climb_break` request carries the reported date and reason plus three plain-text strings composed at request time in `frontend/src/lib/broken-climbs.ts` (the successor name `Name - post break (YYYY)`, the notice appended to the original's description, and the successor's description). The queue shows them verbatim and `applyClimbBreak` writes them unchanged, so a later rename never alters them; nothing in the data model links the two climbs. Sends and journal entries dated on or after the reported date move to the successor in the same batch: a send dated after the break moves with all of that climber's later entries (ascent included, which the journal guard permits once no send remains on the original), while a climber whose send predates the break but who logged later sent repeats gets a fresh send on the successor so those repeats can follow. That send is undated with no rating or comment: dating it would leave a dated send without an ascent entry, which the guard forbids creating afterwards, and an undated send with dated repeats is already a supported state. Undated sends stay. Once `climbs.broken_on` is set, only ascents dated strictly before it may be logged: undated sends are refused too, since they cannot be shown to predate the break, and imports refuse such rows outright: the match step resolves them to the terminal `broken` state naming the climb and its break date rather than sending the user hunting for the post-break climb, and a row that still reaches the server is reported per row (`ImportResult.broken`) rather than failing the batch. `assertLoggableOnClimb` gives the friendly error; the `*_reject_after_break_*` triggers from migration 0044 are the backstop and watch inserts and date/climb changes only, so legacy undated sends stay editable. A merge keeps a colliding source send's videos on the surviving send when that send has none. Broken climbs can't be merged, and approval auto-rejects pending merges that name the climb as source or target, along with other pending break reports for it; pending edits, moves and deletes stay valid. An admin merge applies with no pending request to reject, so `apply_merge.sql`'s batch guard also requires both climbs to still be unbroken — `climbUnchanged` pins only id, type and area, so a break committing between validation and commit would otherwise delete a newly broken source or fold sends into a newly broken target. The "Broken" chip is driven by the column, never by description text.
