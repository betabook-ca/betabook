# Working on Betabook

Betabook is a Rust Cloudflare Worker serving a React Router SPA backed by D1 and R2. Use the [development guide](../.agents/skills/betabook-dev/SKILL.md) for setup, accounts and deployment.

## Code map

| Location                     | Responsibility                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| `backend/domain/src/`        | Domain rules, grades, validation, credential handling and SEO                      |
| `backend/db/src/`            | D1 and native SQLite queries, authorization predicates and transactional mutations |
| `backend/worker/src/`        | HTTP routes, sessions, request state, scheduled exports and binding adapters       |
| `frontend/src/`              | React Router routes, shared UI, navigation and domain presentation                 |
| `backend/migrations/`        | Canonical SQL migrations used by Wrangler and native tests                         |
| `tests/worker/`, `tests/ui/` | Workerd HTTP behavior and browser tests                                            |
| `infra/cloudflare/`          | Cloudflare infrastructure managed through OpenTofu and Spacelift                   |

## Runtime

The root Wrangler configuration serves the Rust release Worker and the assets from `dist-spa/`. Axum handles HTTP requests. The scheduled handler streams the public catalog to R2. `pnpm build` uses mise's pinned Rust toolchain and worker-build. Vite prerenders About and the published Terms using the same components as the SPA. CI packages the release once, tests it in workerd, and reuses those artifacts for browser tests and deployment.

Vite compiles client components and hooks with the native React Compiler in `@vitejs/plugin-react` and `oxc-transform-react`. The SPA build checks that a shipped route imports React’s memoization runtime. Recoverable compiler diagnostics name functions left unoptimized, while fatal transform errors fail the build. `pnpm lint` enforces the recommended React Compiler rules available in Oxlint. The release browser tests exercise the compiled assets. [React lint rules](https://react.dev/reference/eslint-plugin-react-hooks)

## Boundaries and conventions

- Keep business rules in the domain crate and parameterized queries in the database crate. Enforce ownership, privacy and scope predicates in the SQL that reads or writes the affected rows.
- HTTP handlers authenticate members and validate inputs. The SPA uses Worker loaders, action results and React Router to keep its pages in sync.
- Keep server credentials in Worker bindings and redact personal information, session tokens and share links from observability reports.
- `frontend/src/components/ui/` must not import feature components. Reuse its primitives and the existing HeroUI/Tailwind tokens in `frontend/src/spa/globals.css`.
- Store user-written Markdown as source. For HTML sent by the Worker, use `render_safe_markdown` in `backend/domain/src/markdown.rs`. For React previews, use `frontend/src/components/ui/markdown.tsx`. Escape raw HTML, turn images into links to avoid third-party requests and permit only absolute HTTP, HTTPS or mailto links.
- Import boundaries, cycles, duplicates, and relative-parent imports are checked by [`oxlint.config.ts`](../oxlint.config.ts). Use `@/` for cross-directory imports; sibling imports are allowed.
- Public catalog reads expose area/subarea/route names and hierarchy, area and route descriptions, route grades and disciplines, and each climb's whole-catalog send aggregates (average rating and logged-ascent count). Climb lists may therefore filter and order on any of those, including rating and ascent count; area lists have none of the climb columns and reject them. Signed-out climb pages also list the latest 10 sends through `get_public_sends_for_climb`, anonymous with a month-only date and no commentary unless the climber shares send commentary with Everyone from a public profile, and the climb's newest send videos through `get_climb_videos` with a null viewer, which applies that same Everyone rule. Every other send read and the average suggested grade require a session, except the owner's share-link preview and the project share page described under Privacy. Member APIs and page metadata authorize before reading protected data. Locked pages show Sign in/Sign up callouts. Keep authorization at the query and HTTP boundaries.
- Member routes use `require_member_session` in `backend/worker/src/auth/session.rs` to verify the session and current terms acceptance in D1. Admin routes also check the role and enforce area scopes in SQL. Use `resolve_optional_session` only where identity is optional or the user must be able to act before accepting current terms. Keep `/terms`, its archives, `/accept-terms`, contact and account recovery reachable before acceptance.
- Respect the browser targets in `package.json` and the library baseline in `tsconfig.json`. New built-in JavaScript APIs are not automatically polyfilled.

## Data rules to preserve

- **Grades:** `climbs.grade`, `sends.suggested_grade` and `goals.grade` are native ordinals into `BOULDER_HUECO`/`ROPE_YDS` in `frontend/src/lib/grades.ts`, whatever a climber chooses to read. `user.boulder_grade_scale`/`rope_grade_scale` (`frontend/src/lib/grade-preferences.ts`) only change labels and pickers: Rust formats grades with `GradePreferences` in `backend/domain/src/grades.rs`, and React components use `useGradePreferences` and `GradeLabel`. Where Font or French prints two ordinals alike, a picker submits the larger ordinal (`gradeOptions`) and `parseGrade` resolves text the same way. SEO, exports, moderation summaries and demo fixtures stay native. Every climb has a listed grade and every send a suggested grade: climb create and edit validation (`validateNewClimbInput`, `validateClimbEditInput`) and `validateSendInput` require them, a new imported send or a climb break's repeat-only send without one takes the climb's listed grade, and an import overwrite with no usable grade keeps the send's current one. Migration 0054 is the backstop: `climbs_require_grade_*` rejects a null grade, and `sends_fill_suggested_grade_*` fills a null suggested grade from the climb rather than aborting, so a worker deployed before it keeps working. Both columns remain nullable in SQLite. Rebuilding `climbs` solely to add `NOT NULL` can cascade deletes, so preserve the trigger constraints.
- **Ascent styles:** boulder sends are `redpoint` or `flash` only; `onsight` is a rope-only style. `ascentStylesFor` in `frontend/src/lib/sends.ts` drives the pickers and `validateSendInput`, imports coerce a boulder onsight to flash, and the `sends_reject_boulder_onsight_*` triggers from migration 0042 are the backstop. Analytics show flashes and onsights as separate stat cards and as two lines on one rate-by-grade chart; `cardAppliesTo` in `frontend/src/lib/analytics-layout.ts` leaves the onsight card out of bouldering, and the chart draws the flash line alone there.
- **Sends and journal entries:** `sends` has one row per user/climb, including undated sends. `journal_entries` records climb sessions and training; `isAscent` distinguishes the original dated ascent from repeats. The original ascent mirrors the send's date and comment, while repeats do not add another send or rating. Keep writes consistent through atomic D1 batches in `backend/db/src/journal.rs` and `backend/db/src/sends.rs`. Check the SQL guards and `backend/db/tests/migrations_and_queries.rs` when changing logging, imports, or merges.
- **Privacy:** Login is required for all profiles, journals, per-user statistics, and every send beyond a signed-out climb page's anonymized latest 10. The one profile exception is the owner's share link, `/users/{id}?share=<token>`: while its token in `profile_share_links` is current and the profile isn't private, a signed-out holder sees the owner's name, avatar, hardest sends, send count and latest `SHARED_PROFILE_SENDS` sends, with commentary only where it is shared with Everyone (`get_share_link_owner`, then the same `get_sends_for_user_page` predicate as a null viewer). Shared pages use the same components and layout as the signed-in profile. `SharedProfileHeader` renders the same heading and tabs, with a sign-up invite instead of the friend button, and only the tab the link can open, Sends. The profile link opens no trips: each trip has its own link (below). Journals, trips, projects, analytics, friends and the rest of the history require sign-in, and the link preview shows only the name. The link description in `ShareProfileControls` must list everything these pages show, so update it before adding anything to them. Resetting the link or making the profile private rotates the token in SQL, so earlier links and QR codes stay dead after the profile is public again. An account created from a current link records its owner in `user.referred_by` and, once verified, sends that owner a pending friend request unless their profile is private at that moment (`welcome_new_account_once`). Catalog names, hierarchy, area/route descriptions, route grades, disciplines, and each climb's average rating and logged-ascent count are public. The stored `public` audience is displayed as Members (signed-in Betabook users); `everyone`, offered only for send commentary, also reaches signed-out visitors and names the climber on public send rows. `canViewUser` in `frontend/src/lib/user-visibility.ts` controls profile visibility. Journal queries take owner/viewer IDs and read current permissions in SQL; do not pass cached privacy snapshots. A private profile is visible only to its owner, but climb send lists keep its sends as anonymous rows with no user ID, name, commentary, or exact date, keyed by negative list position rather than the sequential send ID. Journal and goals audiences are Only me, Friends, and Members; the same permission governs finished goals in friends’ activity feeds. Climb lists have the same three audiences in one setting, `user.climb_list_visibility` (default Friends), that `climb_lists_visible_sql` applies to every list read and to the profile's Lists tab. Each list may also have its own link, `/lists/{token}` in `climb_list_share_links`, which opens that one list whatever the setting says and shows its name, description, climbs and grades, and the owner's name; `CLIMB_LIST_SHARE_SENTENCE` must list everything that page shows. Client components on that page get the token, never the list id. A list's sent state and sent filter are the reader's own `sends`, never the owner's. Copying is a snapshot: `climb_lists::copy` rechecks the setting or a live token inside the write and keeps no link to the source. Friends requires an accepted mutual relationship in `friendships`; pending requests grant no access. Use `can_read_journal` for current page/metadata authorization and the same `journal_visible_sql` predicate inside data reads so stale props cannot bypass removal. Companion tags follow the tagging author's audience, not the companion's: `companions_json_sql` names a tagged friend to every reader of the entry, regardless of the companion's journal audience, hiding a tag only after self-removal or an ended friendship. A private profile is deliberately not an opt-out here: it governs the profile page, which authorizes its own viewer, so the name is shown and linked to any reader of the entry, and a signed-in reader can learn a private climber's name this way just as a friend request already reveals a private requester's. Privacy is therefore never an eligibility question when tagging: `search_companion_friends` and `journal_companions_insert_guard` weigh only an accepted friendship and the ten-tag cap. Keep guard conditions to facts that cannot change after tagging: re-saving an entry re-sends its unchanged tags, and BEFORE INSERT runs even where ON CONFLICT DO NOTHING makes the row a no-op, so anything else aborts the author's next save. Send commentary has an independent audience enforced by `send_comment_visible_sql`, including mirrored ascent notes and retained notes after deleting or merging sends. A send's videos are part of its commentary: `sends.videos` holds up to five canonical YouTube or Instagram links as a JSON array (`frontend/src/lib/send-video.ts`; migration 0052's triggers reject any other shape, host or character), and every read selects it under the same `send_comment_visible_sql` as the note beside it — climb and public send rows, the Sends tab and share-link profile, the feed, the ascent entry in the journal, and `get_climb_videos` (one row per video) for a climb page's video row — so they never reach an anonymous row or a private profile's viewers. Only an ascent entry carries them; repeats and sessions have no send of their own. Rendering re-parses each stored link with `readSendVideo` and builds player URLs from the extracted id alone, and nothing is requested from YouTube but a poster (sent without a referrer) until the viewer presses play. Instagram lets no other site show the cover of a reel, so where the feed shows the one Instagram video of a send in place it loads the Instagram player with the page. In list rows, rows of several videos and the video row of a climb, Instagram is requested only after a press. Forms send the list with a `videosChanged` marker, so a form without one leaves the stored videos alone. Project share pages don't show videos: their consent copy predates them, so adding them there changes the copy first. A trip link shows videos with the rest of the commentary it overrides. New accounts default to Members commentary and Friends journal entries and trips; member-visible send facts retain profile visibility; per-climb aggregates are public. Exports are owner-only, and so is the Projects tab, with one deliberate exception: a project share link. `project_share_links` (migration 0048) holds one row per pinned project, keyed by a `lower(hex(randomblob(16)))` token that is the whole of `/projects/{token}` — no user or climb id is in the URL. It carries no audience on purpose: a link cannot enforce who holds it, and labelling one Friends or Members would borrow the journal audience's words for something that does not mean the same thing, inviting a climber to treat a forwardable URL as a feed setting. Anyone holding a live token can read it, signed in or not. What can revoke it is in the `READABLE` predicate in `backend/db/src/projects.rs`, applied inside every read: `expires_at`, written by `datetime('now', …)` in SQL or null for indefinite, and the owner not being private. `shared_project` resolves a token to a status and the project in one read, and neither it nor the session read takes a viewer at all, so there is no audience check to get wrong; it selects the owner's name to tell an expiry from a closed profile, and the session query reapplies the predicate. Worker metadata runs the same predicate as the page, so a dead or expired link previews as nothing rather than naming the climber to a channel it was pasted into. A share deliberately overrides the owner's own audiences for that one climb — both `journal_visibility` and `send_comment_visibility` — and that is the feature: the page shows the project as the owner's own board shows it, including send commentary, ascent entries, journal entry ids, and the send with its exact date, rating, suggested grade, grade feel and comment. The shared session query therefore matches the project board's aggregate exactly, so a project cannot report one session count on the owner's card and another on the page that card links to. The consent this rests on is the share dialog's "Anyone with the link sees your sessions, notes and send", said before a link exists and shaped like the profile share control's one-line description; anything added to `SharedProject` has to stay inside what those three words already cover, or the copy changes first. One thing does not travel: companion tags, because they name third parties who did not agree to the link and who never saw the dialog. The owner's email stays out too; their user id does not, since the page links their profile, which a live link already implies is public. The composite foreign key to `pinned_projects` means a link cannot outlive its pin: untracking, deleting the climb and deleting the account all revoke it, `apply_merge.sql` moves the row to the surviving climb with its token so a merge does not silently break a link, and a trigger deletes every row when a profile goes private, so links shared beforehand stay dead once it is public again. `share_project` enforces the pin and the private check inside the INSERT rather than before it, since a session carries no `is_private` and a check in TypeScript would leave a window for a link written just after the profile closed; it returns the deadline the database computed so the dialog reports when the link actually dies. A trip is a date range with a name, a description, Markdown notes and a link to a shared Google Photos album (migrations 0049 and 0051). It has no entries of its own: its sends and journal entries are the ones dated within the range. Trips live at `/users/{id}/trips/{tripId}`, with analytics at `/analytics` under that. The trip page shows the album, the notes and a card for each day with something logged, and has no tabs or filters. Each card's header names the day, lists the crags its rows were at (each climb's own area name, joined by a middle dot, no ancestors) and counts what it lists. The Sends tab's sort-direction arrow (`SortDirectionButton`, ascending for oldest first) at the end of the heading line orders them oldest or newest first. The server always sends the days oldest first and `TripDayOrderProvider` reverses them in the browser, so switching fetches nothing; it replaces the current React Router entry with `?order=newest`, keeping the rest of the query, and a page opened with it (`parseTripDayOrder`) starts in that order. Rows within a day keep the order they were logged. Under each day, `groupTripDays` (`frontend/src/lib/trip-days.ts`) interleaves sends with journal entries in the order they were logged, and a send takes the place of its ascent entry, which only repeats it; other entries for that climb the same day, such as failed sessions, stay. Each day header counts its rows the way their chips name them (sends, repeats, sessions, training). Readers without journal access get the sends alone. The page reads at most `TRIP_DAYS_LIMIT` sends and entries each; a longer trip shows its latest complete days (or, if a read reaches only one day, that day in part) and links to the Journal and Sends tabs. Apart from `order`, URL params are ignored, and `withTripWindow` always applies the trip's dates, so neither `?dateFrom=` nor `?order=` can change the range. The entry and send counts link to the Journal and Sends tabs filtered to the trip's dates (`tripLogbookHref`), and the same line ends with a link to the trip's analytics once something is logged. Trip analytics reuse `AnalyticsDashboard` with `TRIP_ANALYTICS_LAYOUT`, a fixed layout with tiles for sends, hardest, flash, onsight (rope only) and days out, in that order so the share image's default first four include onsight on rope trips, and the grade pyramid. Tiles and charts that compare months or years are left out. Trips have their own audience, `user.trip_visibility` (Only me, Friends or Members; Friends by default for every account, migration 0055), set under Account → Privacy. It is independent of the journal and commentary audiences: it decides who can open the trips without a trip link and nothing else. Trip queries apply `trips_visible_sql` to member reads. Profile access determines whether the Trips tab is visible and whether the viewer can open the list and trip pages. A private profile still overrides it. Anyone the trip audience allows can open the trip, its sends and its analytics. The profile share link does not open trips. Journal and trip access come from one `get_profile_access` read per request. Anyone allowed by `can_read_journal` also gets the journal entries under each day, entry counts, day counts and tagged friends; the entries are read through `get_journal_page`, which applies `journal_visible_sql` again. Notes are visible to the owner and their accepted friends, and to the trip's link. The journal audience doesn't apply to notes. These checks are in the SQL in `backend/db/src/trips.rs`. Journal counts are null and `hasNotes` is 0 when the viewer lacks access, and `member_notes` checks the viewer’s permission again in its own query. The description is one line of up to `MAX_TRIP_DESCRIPTION` characters, visible to anyone who can open the trip. Album photos are also visible to anyone who can open the trip. Google has no embed and blocks iframes, so `loadAlbumPhotos` reads the album page for photo URLs, follows redirects only within Google Photos, and caches the result in the Cache API for an hour. Photos aren't stored or proxied. The viewer's browser loads them from Google with no referrer, because a trip link's URL is its token. A video in the album (`readAlbumPage` reads its length from the item's data) plays in place: its poster frame is the photo URL, and `=m22` on that URL redirects to a 720p MP4 stream that needs no Google session. Google refuses that stream when any referrer is sent, and a `video` element can't set a referrer policy, so `TripAlbumVideo` renders the player in a sandboxed `srcdoc` iframe whose own `<meta name="referrer">` is `no-referrer`. At rest the tile is the poster with the length; a tap or click anywhere plays it and turns the browser's controls on. The controls are off at rest because they swallow taps on a small tile. Nothing loads until play. If the stream errors, the poster links to the album. A trip link is the one way to show a trip to someone outside the trip audience, signed in or not. `trip_share_links` (migration 0050, emptied by 0056 so links from the first version, removed in #353, stay dead) holds one row per trip, keyed by a `lower(hex(randomblob(16)))` token that is the whole of `/trips/{token}`, with its analytics at `/trips/{token}/analytics`. It follows the project link in every rule: no audience; the share predicate in `backend/db/src/trips.rs` (not expired, owner not private) inside every read; `shared_trip` resolving the token to hidden, expired or visible with the trip, its counts and its notes in one read; `trips::share` checking ownership and privacy inside the INSERT, keeping the token when renewing a live link but making a new one once it has expired, so a link the owner let lapse stays dead; `trips::unshare` deleting the row, without the write rate limit, since revoking only reduces exposure; the composite foreign key deleting the link with its trip; `trip_share_revoke_on_private` deleting every row when a profile goes private; the metadata handler running the same predicate, so a dead link previews as nothing; and a `/trips/` terms exemption. The owner's trip page has the Share button (`TripShare` over `ShareLinkDialog`, reading `trips::owner_share`). `trips::owner_share` returns the link only while it is live, on the same `datetime('now')` comparison as the shared page, so the button reads Shared only when the page would open, and on a private profile it says sharing is off instead of offering a link. The owner opening their own link, live or expired, is redirected to their trip page, where the dialog renews it. The page shows the trip the way the owner's own page shows it: the header, album, notes, every day with its sends and journal entries, and the analytics, overriding the owner's journal and commentary audiences for that trip. Each send, journal and analytics query uses `TripReader::window` in its WHERE, which checks the token, its expiry, the owner's privacy and the trip's current dates in the statement that selects the rows (current on purpose: a link shares the trip as it evolves, so moving or extending its dates widens what the link shows), and selects with the owner as the viewer so commentary and videos match the owner's view. What it leaves out is everything that would go further than the trip: the trips list, the Journal and Sends links on the counts and the long-trip notice, hashtag links into the Journal (`TripDays`' `forLink`), the owner's controls, and tagged friends (shared journal queries omit companions, and the trip’s companion list is empty), who never saw the dialog. Nor does any trip or entry id: client components on the page are given none (`TripStatusChip` gets the dates, `TripNotes` gets `tripId` only to edit, `JournalCompanions` and `TripCompanions` render only with someone to name), and on the link's page day rows are keyed by climb id or position. The owner's page keys journal rows by entry id, so open dialogs stay with their entry. The consent is the dialog's "Anyone with the link sees this trip: its notes, photos, journal entries, sends and analytics" (`TRIP_SHARE_SENTENCE`), so anything added to `SharedTrip` changes it first. Unlike the profile link, a trip link records no referral on sign-up, like a project link. Only the owner can create, edit or delete a trip or its notes. Actions scope every write by `user_id`. Tagged friends use `trip_companions` (migration 0051), which has the same columns, guards, ten-tag cap and self-removal tombstone as `journal_companions`. The trip query returns them to anyone who can read the owner's journal, and `trips::save` writes them in the same batch as the trip. If the trip insert is skipped because the user is at their trip limit, `last_insert_rowid()` is stale, so the tag insert also checks `changes()`. A friend request reveals the requester's name/avatar to its recipient's private Friends list, even for a private requester; it grants no access to that person's private profile or history. Both participants can see an accepted connection; either can remove it. Climber suggestions (`get_climber_suggestions`) are friends of accepted friends: a private profile is never suggested and never lends its connections, anyone with a pending request either way is excluded, and a suggestion shows how many friends are shared but not who, though a viewer with few friends can infer them. An uploaded profile photo is the one data route without a session: `GET /api/avatars/<key>` serves the object to anyone holding the URL, because the same avatar has to render in feeds, friends lists and signed-out share-link previews, and because the Google photo URL it replaces was already public on Google's CDN. New uploads use a fresh random object key. An identical upload can reuse the current photo, including an existing content-addressed photo. D1 atomically returns the image displaced by each replacement or removal so cleanup deletes only the retired object. Cached copies may remain available for the seven-day avatar cache lifetime.
- **Moderation:** signed-in users can create areas/climbs and edit descriptions immediately. Names, climb discipline/grade, deletion, moves, reparenting, merges, and broken-climb reports use `backend/worker/src/routes/moderation.rs` and `backend/db/src/moderation/mod.rs`. Admin role alone is insufficient: grants in `admin_area_scopes` cover subtrees, and operations spanning areas need coverage for every affected area. Preserve scope checks, self-review restrictions, and validation at application time.
- **Broken climbs:** a `climb_break` request carries the reported date and reason plus three plain-text strings composed at request time in `frontend/src/lib/broken-climbs.ts` (the successor name `Name - post break (YYYY)`, the notice appended to the original's description, and the successor's description). The queue shows them verbatim and `applyClimbBreak` writes them unchanged, so a later rename never alters them; nothing in the data model links the two climbs. Sends and journal entries dated on or after the reported date move to the successor in the same batch: a send dated after the break moves with all of that climber's later entries (ascent included, which the journal guard permits once no send remains on the original), while a climber whose send predates the break but who logged later sent repeats gets a fresh send on the successor so those repeats can follow. That send is undated with no rating or comment: dating it would leave a dated send without an ascent entry, which the guard forbids creating afterwards, and an undated send with dated repeats is already a supported state. Undated sends stay. Once `climbs.broken_on` is set, only ascents dated strictly before it may be logged: undated sends are refused too, since they cannot be shown to predate the break, and imports refuse such rows outright: the match step resolves them to the terminal `broken` state naming the climb and its break date rather than sending the user hunting for the post-break climb, and a row that still reaches the server is reported per row (`ImportResult.broken`) rather than failing the batch. `assertLoggableOnClimb` gives the friendly error; the `*_reject_after_break_*` triggers from migration 0044 are the backstop and watch inserts and date/climb changes only, so legacy undated sends stay editable. A merge keeps a colliding source send's videos on the surviving send when that send has none. Broken climbs can't be merged, and approval auto-rejects pending merges that name the climb as source or target, along with other pending break reports for it; pending edits, moves and deletes stay valid. An admin merge applies with no pending request to reject, so `apply_merge.sql`'s batch guard also requires both climbs to still be unbroken — `climbUnchanged` pins only id, type and area, so a break committing between validation and commit would otherwise delete a newly broken source or fold sends into a newly broken target. The "Broken" chip is driven by the column, never by description text.
- **Statement size on D1:** SQLite copies a CTE body into every place that names it, including the CTEs inside it. Production D1 keeps one count per statement of the FROM items it expands: each copied CTE body and each subquery with a FROM clause, flat or nested. It checks that count against `SQLITE_LIMIT_EXPR_DEPTH` (100) when it resolves a CTE reference, so a statement with 120 small subqueries and one CTE reference after them fails, while the same statement with the reference first passes ([cloudflare/workerd#8389](https://github.com/cloudflare/workerd/issues/8389)). Since 2026-11-08 ([cloudflare/workers-sdk#16786](https://github.com/cloudflare/workers-sdk/issues/16786)) a statement over the limit fails as a whole with `VIEWs and/or subqueries nested too deep`, and `AS MATERIALIZED` does not avoid it. Naming a CTE once is not enough on its own: count the subqueries around it too. Name each CTE once where you can. Take counts, ranks and positions from window functions over one CTE instead of joining it to an aggregate of itself, and carry columns forward instead of joining an earlier CTE again. Visibility predicates such as `journal_visible_sql` are `EXISTS` subqueries, so each copy of a CTE that uses them adds their tables as well. `get_feed_page` is the worked example: it named `activity` three times and failed in production. A workerd older than production D1 runs such a statement without error, so check a large new statement on a current workerd.
- **Database-managed state:** migrations own FTS synchronization, send aggregates, area cycle guards, journal/send invariants, and project, trip and list share revocation when a profile goes private. Do not replace these with partial application-side updates. Account deletion has explicit cleanup in `backend/db/src/auth.rs` to preserve aggregates. Successful mutations refresh affected SPA views through the action client in `frontend/src/spa/lib/actions-client.ts`.

Versioned SQL in `backend/migrations/` defines the schema, including indexes and triggers. Run `pnpm db:generate add_feature` to create the next numbered SQL file, then write and review the migration. Keep existing migration names and contents intact. CI applies migrations before deployment, so the running Worker must remain compatible. Run `pnpm db:migrate:local` after pulling or adding migrations. `pnpm setup` skips migration for an existing database.

Keep `wrangler.jsonc`, `.dev.vars.example`, and the checked-in `cloudflare-env.d.ts` aligned when changing bindings or environment variables. Generated `worker-configuration.d.ts` is optional for local validation and must not become a build prerequisite. Zone, DNS, and D1 database resources belong in [`infra/cloudflare`](../infra/cloudflare/AGENTS.md); Worker settings, bindings, and custom domains stay in `wrangler.jsonc` because every deploy overwrites them.

## Routes and metadata

Register HTTP routes in the Rust router and client routes in `frontend/src/spa/app.tsx`. Entity pages canonicalize slugs, compose metadata at the edge and inline bootstrap data for the client. Share pages check the current owner and token state before rendering metadata. Preserve HTTP status codes, private/no-store headers and generic signed-out metadata on member pages. Keep public landing routes synchronized with sitemap and terms exemptions.

## Design system and UI regressions

Use [the design system entry point](design-system.md) to find design principles
and real component examples in Storybook or the `betabook-storybook` MCP. Inspect
local stories for changes on the current branch. Reuse the production primitives
and theme tokens demonstrated there.

Follow [story authoring rules](component-testing.md#story-rules) when adding or
changing examples. Keep design guidance with the foundation/pattern stories and
component examples; routine UI PRs should not update `docs/design-system.md`.
Explain intentional design changes in the work summary or PR.

For UI changes, run the affected `tests/ui` spec files in addition to the normal
checks. Prefer unit/component tests for behavior and browser assertions only for
real rendering or native interactions. Do not collect passing screenshots. Leave
the full browser suite to CI's **UI reference** job; it is too slow to run
locally. Passing assertions do not replace visual review. Never loosen an
assertion solely to make a regression pass.

## Product tutorials

For each user-facing feature or workflow change, decide whether to update an existing lesson, add a step, create a tour, or leave tutorials unchanged. Record the choice and reason in the plan or PR, and fix any lesson made inaccurate by the change.

Read [docs/product-tours.md](product-tours.md) before changing a tutorial. It covers registration, stable step IDs and targets, versioned updates, navigation, layout, and verification. Reuse the app's display components and `frontend/src/lib/product-tour-demo.ts` fixtures; sample controls stay local and sample IDs must never reach real links or writes. Keep the guide separate from the demo and confine spotlight dimming to the demo pane. Verify navigation/replay, keyboard focus, mobile layout, and that demo interactions do not change account data.

## Testing and validation

Before adding or changing tests, read [Choosing and writing tests](component-testing.md). Select the runner by path and suffix, matching `.dom.test` before `.test`:

| Path and suffix                                                                                    | Required guidance                                                                                |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `*.dom.test.{ts,tsx}` in `frontend/src/components/`, `frontend/src/hooks/` and `frontend/src/spa/` | [jsdom rules](component-testing.md#jsdom-rules) for mounted behavior.                            |
| Other `frontend/src/**/*.test.{ts,tsx}`                                                            | [Unit test rules](component-testing.md#unit-test-rules) for frontend logic and static markup.    |
| Rust crate tests and `tests/worker/*.ts`                                                           | [Workers rules](component-testing.md#workers-rules) for domain, database and HTTP behavior.      |
| `tests/ui/*.spec.ts`                                                                               | [Browser rules](component-testing.md#browser-rules) for native interactions and app integration. |
| `*.stories.tsx`                                                                                    | [Story rules](component-testing.md#story-rules) for reproducible examples.                       |

The runner configs control collection; `.tsx` alone does not select jsdom. Check the guide before using a new directory or suffix. Keep each assertion in the least expensive environment that can reproduce its regression, and delete superseded Playwright cases when moving behavior to jsdom.

- Follow red–green for behavior changes: write a focused test, observe a failure caused by the missing/incorrect behavior, implement the fix, then confirm green. Syntax, import, setup, and unrelated failures do not count as red.
- When adding or strengthening tests for existing behavior, temporarily introduce a targeted production regression and observe the expected failure, then restore the code and confirm green. Never leave the deliberate regression in the diff.
- Exercise real behavior and assert specific results, identities, state changes, or required side effects. Avoid fixture-only assertions, implementation copies, source-text checks, and mocks that replace the subject. Collection assertions must establish the expected records are present; empty loops or `every()` are insufficient.
- Cover relevant boundaries and failures, especially authorization, privacy, and persistence. Await asynchronous work and verify rejected writes leave state unchanged. Keep mocks at external boundaries and each test independent with its own preconditions.
- `pnpm test` and `pnpm check` run both Vitest projects. Use `pnpm test:components` for jsdom and `pnpm test --project=unit` for Node unit tests. Neither requires a production build or local seed. Keep the focused run's collection and result in the work summary; an uncollected test is not passing coverage.
- Record the focused red and green commands and outcomes in the work summary or PR. Do not claim red–green from a passing-only run. Documentation-only edits need formatting and reference checks, not artificial runtime tests.

Before committing, run `pnpm check` (lint, format check, dead code, typecheck, and tests). `pnpm deadcode:prod` is a separate audit for exports retained only by development/test entrypoints. Use `pnpm format` to fix formatting. The pre-commit hook formats staged files and the pre-push hook runs `pnpm check`.

For changes affecting runtime code, dependencies, routes, or Cloudflare configuration, also verify `pnpm build`, which CI runs after its checks. Use `pnpm preview` when the behavior needs testing in the built Workers bundle. See the [`betabook-dev` skill](../.agents/skills/betabook-dev/SKILL.md) for the complete command guide.
