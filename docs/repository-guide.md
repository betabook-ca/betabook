# Working on Betabook

Betabook is a climbing logbook and crag database built with Next.js 16 App Router, React 19, HeroUI, Tailwind CSS, Cloudflare Workers/vinext, D1/Drizzle, and Better Auth. Read [README.md](../README.md) for setup, local accounts, scripts, and deployment. `package.json` and the config files are the source of truth for tooling.

## Code map

## Runtime

[vinext](https://vinext.dev) builds and serves the app: a Vite plugin that reimplements the Next.js API, with the Cloudflare Vite plugin running every server environment in workerd, in `pnpm dev` as in production. The `next` package stays installed only for its types, `@storybook/nextjs-vite` and the Workers tests; what `next/*` imports do in the app comes from vinext's shims in `node_modules/vinext/dist/shims`, so check there when behavior disagrees with the Next.js docs.

- Read bindings and vars through `getCloudflareEnv()` in `lib/cloudflare-env.ts`, never `cloudflare:workers` directly, so tests can substitute values. It works outside requests too, including the cron handler.
- Pages can't reach the Worker's `Request`. `worker.ts` copies `request.cf.timezone` into a header that `getRequestTimezone()` reads, discarding any client-sent value; add other edge facts the same way.
- Server components import HeroUI style helpers from `@heroui/styles` and components by subpath (`@heroui/react/chip`). The RSC build walks the whole `@heroui/react` barrel and rejects its client-only calendar code.
- `patches/vinext@1.0.0-beta.12.patch` keys vinext's streaming-metadata `Suspense` by route. Unkeyed, sibling routes share one already-revealed boundary, so a navigation holds the old page until the new page's `generateMetadata` resolves. 1.0.0 still needs it; carry it across upgrades until upstream keys the boundary.
- `generateMetadata` and route handlers run outside the React render's cache scope, so React's `cache()` dedupes only within the page tree and a metadata read repeats its page counterpart against D1. Memoize per-request loaders with `requestMemo` in `lib/request-memo.ts` (vinext's `cacheForRequest` underneath, covering metadata, template and page; inert outside a request). The scope also spans a server action and the rerender that follows it, and nothing invalidates an entry, so an action must not read through a memoized loader whose answer its own write changes. Tests enter that scope with `runWithRequestContext(createRequestContext(), fn)` from `vinext/shims/unified-request-context`.
- Known vinext divergences the code works around: a root layout's `title.template` applies to the root page, so `app/page.tsx` uses `title.absolute`; `geist/font/sans` 404s in `pnpm dev`, so `app/layout.tsx` declares the font file itself. Redirects and `notFound()` during render send real 3xx/404 statuses where OpenNext streamed a 200. `next.config.ts` header rules miss `/` (vinext compiles `/:path*` to need a segment) and those thrown redirects and 404s, so the security headers live in `lib/security-headers.ts` and `worker.ts` adds them to every response.

## Boundaries and conventions

- Pages and route handlers load data through `db/queries`; components receive it as props or fetch the app's API routes. Components must not import database clients, queries, or schemas at runtime. Type-only imports are allowed.
- User mutations normally enter through `"use server"` modules in `actions/`, exported through `@/actions`. Validate inputs, authenticate with `requireSession()`, enforce ownership/permissions, and return `Promise<ActionResult<T>>` via `toActionResult`. Internal helpers may throw `ActionError`; unexpected errors must stay generic to the client. Navigate on the client after success rather than throwing `redirect`/`notFound` inside that wrapper.
- `lib/contact-action.ts` is the existing public, unauthenticated action; it uses bot checks and a rate limiter. Better Auth owns its own API mutations. Do not assume every write is in `actions/` or requires a session.
- `actions/` must not depend on `app/` or `components/`. `db/` and `lib/` must not depend on `app/`, `components/`, or `actions/`. `lib/` is not entirely pure: auth, email, account cleanup, and moderation helpers perform server work. Keep pure calculations separate from those services.
- `components/ui/` must not import feature components. Reuse its primitives and the existing HeroUI/Tailwind tokens in `app/globals.css`.
- User-written Markdown is rendered only by `Markdown` in `components/ui/markdown.tsx`. It is stored as Markdown source, never as HTML. Raw HTML is escaped, images become links so nothing loads from another host, and only absolute `http(s)` and `mailto` links are kept. Render it in server components. Client components should load it with `next/dynamic` to keep the parser out of the main bundle.
- Import boundaries, cycles, duplicates, and relative-parent imports are checked by [`oxlint.config.ts`](../oxlint.config.ts). Use `@/` for cross-directory imports; sibling imports are allowed.
- Public catalog reads expose area/subarea/route names and hierarchy, area and route descriptions, route grades and disciplines, and each climb's whole-catalog send aggregates (average rating and logged-ascent count). Climb lists may therefore filter and order on any of those, including rating and ascent count; area lists have none of the climb columns and reject them. Signed-out climb pages also list the latest 10 sends through `getPublicSendsForClimb`, anonymous with a month-only date and no commentary unless the climber shares send commentary with Everyone from a public profile. Every other send read and the average suggested grade require a session, except the owner's share-link preview, recap links, and the project share page described under Privacy. All other data APIs use `withApiSession`, and pages and metadata authorize before reading protected data. Locked pages show Sign in/Sign up callouts. Any future middleware (`proxy.ts`) must not replace real authorization.
- Member page loaders and metadata use `getMemberSession`; actions use `requireSession`, and member APIs use `withApiSession`. These check current terms acceptance in D1, including for existing sessions. Raw `getSession` establishes identity only and is reserved for the template, authentication, and agreement flow; it does not authorize member data. Keep `/terms`, its version archives, `/accept-terms`, contact, and account recovery reachable before acceptance.
- Respect the browser targets in `package.json` and the library baseline in `tsconfig.json`. New built-in JavaScript APIs are not automatically polyfilled.

## Data rules to preserve

- **Ascent styles:** boulder sends are `redpoint` or `flash` only; `onsight` is a rope-only style. `ascentStylesFor` in `lib/sends.ts` drives the pickers and `validateSendInput`, imports coerce a boulder onsight to flash, and the `sends_reject_boulder_onsight_*` triggers from migration 0042 are the backstop. Flash analytics count flash and onsight together via `isFirstTry`.
- **Sends and journal entries:** `sends` has one row per user/climb, including undated sends. `journal_entries` records climb sessions and training; `isAscent` distinguishes the original dated ascent from repeats. The original ascent mirrors the send's date and comment, while repeats do not add another send or rating. Keep writes consistent through `actions/journal-sync.ts`, `actions/send-statements.ts`, and atomic D1 batches. Check the SQL guards and `db/journal-send-sync.test.ts` when changing logging, imports, or merges.
- **Privacy:** Login is required for all profiles, journals, per-user statistics, and every send beyond a signed-out climb page's anonymized latest 10. The one profile exception is the owner's share link, `/users/{id}?share=<token>`: while its token in `profile_share_links` is current and the profile isn't private, a signed-out holder sees the owner's name, avatar, hardest sends, send count and latest `SHARED_PROFILE_SENDS` sends, with commentary only where it is shared with Everyone (`getShareLinkOwner`, then the same `getSendsForUserPage` predicate as a null viewer). Shared pages use the same components and layout as the signed-in profile. `SharedProfileHeader` renders the same heading and tabs, with a sign-up invite instead of the friend button, and only the tabs the link can open. The same link opens the owner's trips list at `/users/{id}/trips?share=<token>` and each trip page, which shows the trip's name, dates, description, album, notes, send count and its latest `SHARED_TRIP_SENDS` sends. These are loaded with a null viewer through `resolveSharedProfile` and `resolveSharedTrip`. Trip analytics and journal-gated data (entries, entry counts, tagged friends) require sign-in. So do journals, projects, analytics, friends and the rest of the history, and the link preview shows only the name. The link description in `ShareProfileControls` must list everything these pages show, so update it before adding anything to them. Resetting the link or making the profile private rotates the token in SQL, so earlier links and QR codes stay dead after the profile is public again. An account created from a current link records its owner in `user.referred_by` and, once verified, sends that owner a pending friend request unless their profile is private at that moment (`welcomeNewAccountOnce`). Catalog names, hierarchy, area/route descriptions, route grades, disciplines, and each climb's average rating and logged-ascent count are public. The stored `public` audience is displayed as Members (signed-in Betabook users); `everyone`, offered only for send commentary, also reaches signed-out visitors and names the climber on public send rows. `canViewUser` in `lib/user-visibility.ts` controls profile visibility. Journal queries take owner/viewer IDs and read current permissions in SQL; do not pass cached privacy snapshots. A private profile is visible only to its owner, but climb send lists keep its sends as anonymous rows with no user ID, name, commentary, or exact date, keyed by negative list position rather than the sequential send ID. Journal and goals audiences are Only me, Friends, and Members; the same permission governs finished goals in friends’ activity feeds. Friends requires an accepted mutual relationship in `friendships`; pending requests grant no access. Use `canReadJournal` for current page/metadata authorization and the same `journalVisibleSql` predicate inside data reads so stale props cannot bypass removal. Companion tags follow the tagging author's audience, not the companion's: `companionsJsonSql` names a tagged friend to every reader of the entry, regardless of the companion's journal audience, hiding a tag only after self-removal or an ended friendship. A private profile is deliberately not an opt-out here: it governs the profile page, which authorizes its own viewer, so the name is shown and linked to any reader of the entry, and a signed-in reader can learn a private climber's name this way just as a friend request already reveals a private requester's. Privacy is therefore never an eligibility question when tagging: `searchCompanionFriends` and `journal_companions_insert_guard` weigh only an accepted friendship and the ten-tag cap. Keep guard conditions to facts that cannot change after tagging: re-saving an entry re-sends its unchanged tags, and BEFORE INSERT runs even where ON CONFLICT DO NOTHING makes the row a no-op, so anything else aborts the author's next save. Send commentary has an independent audience enforced by `sendCommentVisibleSql`, including mirrored ascent notes and retained notes after deleting or merging sends. New accounts default to Members commentary and Friends journal entries; member-visible send facts retain profile visibility; per-climb aggregates are public. Exports are owner-only, and so is the Projects tab, with one deliberate exception: a project share link. `project_share_links` (migration 0048) holds one row per pinned project, keyed by a `lower(hex(randomblob(16)))` token that is the whole of `/projects/{token}` — no user or climb id is in the URL. It carries no audience on purpose: a link cannot enforce who holds it, and labelling one Friends or Members would borrow the journal audience's words for something that does not mean the same thing, inviting a climber to treat a forwardable URL as a feed setting. Anyone holding a live token can read it, signed in or not. What can revoke it is in `readableSql` in `db/queries/project-shares.ts`, applied inside every read: `expires_at`, written by `datetime('now', …)` in SQL or null for indefinite, and the owner not being private. `getSharedProject` resolves a token to a status and the project in one read, and neither it nor the session read takes a viewer at all, so there is no audience check to get wrong; it selects the owner's name to tell an expiry from a closed profile, and the session notes stay behind `getSharedProjectSessions` and its own copy of the predicate. `generateMetadata` runs the same predicate as the page, so a dead or expired link previews as nothing rather than naming the climber to a channel it was pasted into. A share deliberately overrides the owner's own audiences for that one climb — both `journal_visibility` and `send_comment_visibility` — and that is the feature: the page shows the project as the owner's own board shows it, including send commentary, ascent entries, journal entry ids, and the send with its exact date, rating, suggested grade, grade feel and comment. `sharedSessionRowsSql` therefore matches `projectSelect`'s aggregate exactly, so a project cannot report one session count on the owner's card and another on the page that card links to. The consent this rests on is the share dialog's "Anyone with the link sees your sessions, notes and send", said before a link exists and shaped like the profile share control's one-line description; anything added to `SharedProject` has to stay inside what those three words already cover, or the copy changes first. One thing does not travel: companion tags, because they name third parties who did not agree to the link and who never saw the dialog. The owner's email stays out too; their user id does not, since the page links their profile, which a live link already implies is public. The composite foreign key to `pinned_projects` means a link cannot outlive its pin: untracking, deleting the climb and deleting the account all revoke it, `applyClimbMerge` moves the row to the surviving climb with its token so a merge does not silently break a link, and a trigger deletes every row when a profile goes private, so links shared beforehand stay dead once it is public again. `shareProject` enforces the pin and the private check inside the INSERT rather than before it, since a session carries no `is_private` and a check in TypeScript would leave a window for a link written just after the profile closed; it returns the deadline the database computed so the dialog reports when the link actually dies. A trip is a date range with a name, a description, Markdown notes and a link to a shared Google Photos album (migrations 0049 and 0051). It has no entries of its own: its sends and journal entries are the ones dated within the range. Trips live at `/users/{id}/trips/{tripId}`, with analytics at `/analytics` under that. The trip page shows the album, the notes and the sends, and has no tabs or filters. URL params are ignored and `withTripWindow` always applies the trip's dates, so `?dateFrom=` can't change the range. The entry and send counts link to the Journal and Sends tabs filtered to the trip's dates (`tripLogbookHref`), and the same line ends with a link to the trip's analytics once something is logged. Trip analytics reuse `AnalyticsDashboard` with `TRIP_ANALYTICS_LAYOUT`, a fixed layout with four tiles (sends, hardest, days out, flash rate) and the grade pyramid. Tiles and charts that compare months or years are left out. Anyone allowed by `canViewUser` can open the trip, its sends and its analytics. Anyone allowed by `canReadJournal` also gets entry counts, day counts and tagged friends. Notes are visible to the owner, their accepted friends, and anyone with the owner's current profile link, signed in or not (`canReadTripNotes`, `tripNotesVisibleSql`). The journal audience doesn't apply to notes. A signed-out visitor with the profile link gets the trip, its notes and its sends. Signed-in pages don't add the token to their links, so a member who isn't a friend only sees the notes on a URL that includes it. These checks are in SQL (`tripRowsSql` and `tripCountsSql` in `db/queries/trips.ts`). Journal counts are null and `hasNotes` is 0 when the viewer lacks access, and `getTripNotes` applies `tripNotesVisibleSql` again in its own query. The description is one line of up to `MAX_TRIP_DESCRIPTION` characters, visible to anyone who can open the trip. Album photos are also visible to anyone who can open the trip. Google has no embed and blocks iframes, so `loadAlbumPhotos` reads the album page for photo URLs, follows redirects only within Google Photos, and caches the result in the Cache API for an hour. Photos aren't stored or proxied. The viewer's browser loads them from Google with no referrer, because the page URL can contain the share token. A video in the album (`readAlbumPage` reads its length from the item's data) plays in place: its poster frame is the photo URL, and `=m22` on that URL redirects to a 720p MP4 stream that needs no Google session. Google refuses that stream when any referrer is sent, and a `video` element can't set a referrer policy, so `TripAlbumVideo` renders the player in a sandboxed `srcdoc` iframe whose own `<meta name="referrer">` is `no-referrer`. At rest the tile is the poster with the length; a tap or click anywhere plays it and turns the browser's controls on. The controls are off at rest because they swallow taps on a small tile. Nothing loads until play. If the stream errors, the poster links to the album. The owner's trip page has a Share button (`TripShare`, `getOwnTripShareUrl`) that gives the profile link pointed at the trip. It uses the profile's token, not a separate one, so it opens everything the profile link opens, and resetting the link or going private disables it. The URL is only sent to the owner. Only the owner can create, edit or delete a trip or its notes. Actions scope every write by `user_id`. Tagged friends use `trip_companions` (migration 0051), which has the same columns, guards, ten-tag cap and self-removal tombstone as `journal_companions`. `tripCompanionsJsonSql` returns them to anyone who can read the owner's journal, and `saveTrip` writes them in the same batch as the trip. If the trip insert is skipped because the user is at their trip limit, `last_insert_rowid()` is stale, so the tag insert also checks `changes()`. `trip_share_links` (migration 0050) and its `trip_share_revoke_on_private` trigger are no longer used. A later migration should drop both. They stay for now because migrations run before the new worker is live. A friend request reveals the requester's name/avatar to its recipient's private Friends list, even for a private requester; it grants no access to that person's private profile or history. Both participants can see an accepted connection; either can remove it. Climber suggestions (`getClimberSuggestions`) are friends of accepted friends: a private profile is never suggested and never lends its connections, anyone with a pending request either way is excluded, and a suggestion shows how many friends are shared but not who, though a viewer with few friends can infer them. An uploaded profile photo is the one data route without a session: `GET /api/avatars/<key>` serves the object to anyone holding the URL, because the same avatar has to render in feeds, friends lists and signed-out share-link previews, and because the Google photo URL it replaces was already public on Google's CDN. The key is a digest of the stored bytes, so it is unguessable and reveals nothing but the opaque user id, `readProfilePhoto` re-validates its shape before any bucket read, and removal deletes the object — though caches downstream may still answer that URL until the week-long `max-age` in `lib/profile-photo.ts` expires.
- **Recap shares:** `prepareRecapShare` is owner-only and stores a frozen snapshot under a separate random `/r/{token}` grant. A signed-out holder sees only the selected period's cover facts, grade breakthroughs, highest-rated climbs, and chosen Analytics highlights such as a tagged partner's name, shared-day count, or climb session count; no raw send history, commentary, journal bodies or projects cross the link. General Analytics rows omit personal ratings; only the owner-only recap query reads them, and journal highlights use the owner's current journal access while issuing the snapshot. The viewer's Profile link uses the ordinary profile path, never the profile-share token. Every page and cover-image read compares the profile token captured at issue with the current token and requires a public profile. A privacy toggle or profile-link reset revokes old recaps, including after a profile is made public again. Recap HTML sends no-store and no-referrer headers; do not serve token images through the image optimizer or cache a permission check.
- **Moderation:** signed-in users can create areas/climbs and edit descriptions immediately. Names, climb discipline/grade, deletion, moves, reparenting, merges, and broken-climb reports use `actions/moderation.ts` and `lib/moderation.ts`. Admin role alone is insufficient: grants in `admin_area_scopes` cover subtrees, and operations spanning areas need coverage for every affected area. Preserve scope checks, self-review restrictions, and validation at application time.
- **Broken climbs:** a `climb_break` request carries the reported date and reason plus three plain-text strings composed at request time in `lib/broken-climbs.ts` (the successor name `Name - post break (YYYY)`, the notice appended to the original's description, and the successor's description). The queue shows them verbatim and `applyClimbBreak` writes them unchanged, so a later rename never alters them; nothing in the data model links the two climbs. Sends and journal entries dated on or after the reported date move to the successor in the same batch: a send dated after the break moves with all of that climber's later entries (ascent included, which the journal guard permits once no send remains on the original), while a climber whose send predates the break but who logged later sent repeats gets a fresh send on the successor so those repeats can follow. That send is undated with no rating or comment: dating it would leave a dated send without an ascent entry, which the guard forbids creating afterwards, and an undated send with dated repeats is already a supported state. Undated sends stay. Once `climbs.broken_on` is set, only ascents dated strictly before it may be logged: undated sends are refused too, since they cannot be shown to predate the break, and imports refuse such rows outright: the match step resolves them to the terminal `broken` state naming the climb and its break date rather than sending the user hunting for the post-break climb, and a row that still reaches the server is reported per row (`ImportResult.broken`) rather than failing the batch. `assertLoggableOnClimb` gives the friendly error; the `*_reject_after_break_*` triggers from migration 0044 are the backstop and watch inserts and date/climb changes only, so legacy undated sends stay editable. Broken climbs can't be merged, and approval auto-rejects pending merges that name the climb as source or target, along with other pending break reports for it; pending edits, moves and deletes stay valid. An admin merge applies with no pending request to reject, so `applyClimbMerge`'s batch guard also requires both climbs to still be unbroken — `climbUnchanged` pins only id, type and area, so a break committing between validation and commit would otherwise delete a newly broken source or fold sends into a newly broken target. The "Broken" chip is driven by the column, never by description text.
- **Database-managed state:** migrations own FTS synchronization, send aggregates, area cycle guards, journal/send invariants, and project share revocation when a profile goes private. Do not replace these with partial application-side updates. Account deletion has explicit cleanup in `lib/account.ts` to preserve aggregates. Use the existing revalidation helpers in `actions/revalidation.ts` for affected send and journal views.

Edit schema definitions in `drizzle/schema/`, then use `pnpm db:generate` and inspect the SQL. Some indexes and triggers exist only in handwritten migrations, so the TypeScript schema is not a complete description of the database. Add new migrations under `drizzle/migrations/` and keep them compatible with the running worker; CI applies them before deployment. Run `pnpm db:migrate:local` after pulling or adding migrations: `pnpm setup` does not migrate an existing database.

Keep `wrangler.jsonc`, `.dev.vars.example`, and the checked-in `cloudflare-env.d.ts` aligned when changing bindings or environment variables. Generated `worker-configuration.d.ts` is optional for local validation and must not become a build prerequisite. Zone, DNS, and D1 database resources belong in [`infra/cloudflare`](../infra/cloudflare/README.md); Worker settings, bindings, and custom domains stay in `wrangler.jsonc` because every deploy overwrites them.

## Routes and metadata

- Build entity links with `areaHref` / `climbHref` from `lib/slug.ts`; IDs identify records and the optional slug is normalized by the route.
- Earlier compact `/s/{token}` links are a URL-safe encoding of the existing profile-share token, not a second grant. They still redirect without caching to `/users/{id}?share={token}` while current and public. New stats-card captions use `/r/{token}`, a separate frozen recap share checked on every request.
- Decide whether each new page should be indexable. Use `pageMetadata` and the title/description builders in `lib/seo.ts` for indexable pages so canonical, Open Graph, and Twitter metadata stay complete.
- Area and climb pages remain crawlable with names and hierarchy links. Their public queries use explicit field projections; metadata and JSON-LD may contain names, location trails, area/route descriptions, and route grades and disciplines. Never include ratings, activity, or user information in these public payloads.
- Auth pages, new-entry forms, session-gated routes, and all user-profile views must be `robots: { index: false }`. Filter/search variants of otherwise indexable pages should be noindex when query parameters are present, as on `app/page.tsx`.
- Entity pages render `JsonLd` with at least breadcrumbs, using the builders in `lib/seo.ts`. Do not add `AggregateRating` or `Review` markup. Extend `lib/seo.test.ts` for new builders.
- Add new crawlable entity types to `app/sitemap.ts` with count and paginated query helpers. The sitemap index route is `/sitemap-index.xml`. API responses get `X-Robots-Tag: noindex` from `next.config.ts`. [`app/robots.ts`](../app/robots.ts) excludes auth-page crawling (including return-destination variants), homepage search queries, `/search` query variants, area filter/sort queries, and public search APIs, and advertises the sitemap. Canonical catalog pages remain crawlable, and so does the bare `/search`: it is linked from every signed-out page, and a crawler must fetch it to read its noindex. Cloudflare prepends its managed AI crawler policy, enabled in [`infra/cloudflare/zone.tf`](../infra/cloudflare/zone.tf).
- Public product pages (the logbook and import pages) are listed in `lib/landing-pages.ts`, which feeds the sitemap's static paths and `isTermsExemptPath`. Build them from the sections in `components/landing-page.tsx`. When import, privacy or export behavior changes, update `components/import-landing-page.tsx`, `app/climbing-logbook/page.tsx` and the About privacy list.

## Design system and UI regressions

Use [the design system entry point](design-system.md) to find design principles
and real component examples in Storybook or the `betabook-storybook` MCP. Inspect
local stories for changes on the current branch. Reuse the production primitives
and theme tokens demonstrated there.

Follow [story authoring rules](component-testing.md#story-rules) when adding or
changing examples. Keep design guidance with the foundation/pattern stories and
component examples; routine UI PRs should not update `docs/design-system.md`.
Explain intentional design changes in the work summary or PR.

The Analytics calendar starts with all disciplines combined and has its own
multi-select, listing only disciplines with dated activity in the selected years;
the page discipline still scopes grade charts. On Analytics, year and hashtag
filters apply to the calendar and grade charts. The shared recap's hook card
combines disciplines and shows the most active calendar year for an all-time
recap. The cover always has three summary cards. A one-discipline cover splits
Sends and Hardest send into separate cards and fills the third with flash or
first-try rate. A two-discipline cover adds the same Analytics highlight. The
owner sees the Year in review action beside Customize in the Analytics header
only during December in the request timezone. Sharing is fixed to the current
year; there are no monthly or all-time choices, and the server action enforces
the same December window. The social app gets one 1080×1350 hook image. Its link opens responsive,
full-screen pages with no vertical scrolling: a cover, an optional breakthroughs
page, an optional Analytics highlights page, and an optional Favorite climbs
page. Highlights prioritize Favorite partner, Most sessioned climb, and Most
sessions in a day. Favorite climbs ranks the owner's highest-rated routes across
disciplines. The breakthroughs page appears when the climber set any new
lifetime grade bests and contains every
breakthrough across disciplines, grouped under Boulder, Sport, and Trad with
the grade, climb, and date on each card. Long histories use category controls
and batches of six cards on the same recap page. The first graded send is a
baseline. Individual grade pyramids remain on Analytics rather than the recap.

For UI changes, run the affected `tests/ui` spec files in addition to the normal
checks. Prefer unit/component tests for behavior and browser assertions only for
real rendering or native interactions. Do not collect passing screenshots. Leave
the full browser suite to CI's **UI reference** job; it is too slow to run
locally. Passing assertions do not replace visual review. Never loosen an
assertion solely to make a regression pass.

## Product tutorials

For each user-facing feature or workflow change, decide whether to update an existing lesson, add a step, create a tour, or leave tutorials unchanged. Record the choice and reason in the plan or PR, and fix any lesson made inaccurate by the change.

Read [docs/product-tours.md](product-tours.md) before changing a tutorial. It covers registration, stable step IDs and targets, versioned updates, navigation, layout, and verification. Reuse the app's display components and `lib/product-tour-demo.ts` fixtures; sample controls stay local and sample IDs must never reach real links or writes. ## Testing and validation

Before adding or changing tests, read [Choosing and writing tests](component-testing.md). Select the runner by path and suffix, matching `.dom.test` before `.test`:

| Path and suffix                                                                               | Required guidance                                                                                      |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `components/**/*.dom.test.{ts,tsx}`, `hooks/**/*.dom.test.{ts,tsx}`                           | [jsdom rules](component-testing.md#jsdom-rules): mounted client behavior and real hooks                |
| `*.test.{ts,tsx}` under `actions/`, `app/`, `components/`, `db/`, `lib/`, excluding DOM tests | [Workers rules](component-testing.md#workers-rules): calculations, server contracts and migrated D1    |
| `tests/ui/*.spec.ts`                                                                          | [Browser rules](component-testing.md#browser-rules): rendering, native interaction and app integration |
| `*.stories.tsx`                                                                               | [Story rules](component-testing.md#story-rules): reproducible examples; no automatic browser checks    |

The runner configs control collection; `.tsx` alone does not select jsdom. Check the guide before using a new directory or suffix. Keep each assertion in the least expensive environment that can reproduce its regression, and delete superseded Playwright cases when moving behavior to jsdom.

- Follow red–green for behavior changes: write a focused test, observe a failure caused by the missing/incorrect behavior, implement the fix, then confirm green. Syntax, import, setup, and unrelated failures do not count as red.
- When adding or strengthening tests for existing behavior, temporarily introduce a targeted production regression and observe the expected failure, then restore the code and confirm green. Never leave the deliberate regression in the diff.
- Exercise real behavior and assert specific results, identities, state changes, or required side effects. Avoid fixture-only assertions, implementation copies, source-text checks, and mocks that replace the subject. Collection assertions must establish the expected records are present; empty loops or `every()` are insufficient.
- Cover relevant boundaries and failures, especially authorization, privacy, and persistence. Await asynchronous work and verify rejected writes leave state unchanged. Keep mocks at external boundaries and each test independent with its own preconditions; use `test/fixtures.ts` and `test/reset-db.ts` where appropriate.
- `pnpm test` and `pnpm check` run both Vitest projects. Use `pnpm test:components` for jsdom and `pnpm test --project=workers` for Workers. Neither requires a production build or local seed. Keep the focused run's collection and result in the work summary; an uncollected test is not passing coverage.
- Record the focused red and green commands and outcomes in the work summary or PR. Do not claim red–green from a passing-only run. Documentation-only edits need formatting and reference checks, not artificial runtime tests.

Before committing, run `pnpm check` (lint, format check, dead code, typecheck, and tests). `pnpm deadcode:prod` is a separate audit for exports retained only by development/test entrypoints. Use `pnpm format` to fix formatting. The pre-commit hook formats staged files and the pre-push hook runs `pnpm check`.

For changes affecting runtime code, dependencies, routes, or Cloudflare configuration, also verify `pnpm build`, which CI runs after its checks. Use `pnpm preview` when the behavior needs testing in the built Workers bundle. See [README.md](../README.md) for the complete command guide.
