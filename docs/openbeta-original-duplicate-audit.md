# Original Betabook route duplicates after OpenBeta import

Read-only audit of `artifacts/openbeta-2026-09-20-live/preview.sqlite`, using `(area_id, lower(trim(name)), type)` and retaining groups whose maximum climb ID is at most 141206. This reproduces the production finding: **213 groups / 432 original climbs** (208 pairs, four triples, one quadruple). These are pre-existing Betabook collisions, not new OpenBeta IDs. The preview predates the four imported-involved duplicate fixes, but those do not change these 213 original-only groups. This audit made no production changes.

The 213 comprise 146 sport, 65 boulder, and two trad groups. **Nine groups have nonzero `climbs.send_count`, totaling 13 sends**; each pair has sends on only one climb. All nine have identical grades. The preview has no `sends` or `journal_entries` records despite retaining aggregate `send_count`; current production dependencies must be checked before changes. **21 groups have exactly one OpenBeta source link**, and 192 have none. All 213 groups have non-null grades; 210 have meaningful names.

Each name appears only in its pair catalog-wide. Preserve the logged ID if approved for merger.
- **Other logged same-grade candidates:** `Standard Overhang` 10783/86341 (grade 4, one send on 86341), `Shaman` 28749/67255 (16, one send on 28749), `Rifle` 28699/37530 (10, one send on 37530), and `Turf Wars` 70851/110532 (12, one send on 70851). `Standard Overhang Sit` 73789 is a **separate V10 climb** in the same area and must remain separate. [Mountain Project lists Standard Overhang as V3](https://www.mountainproject.com/area/106028873/boulders-little-cottonwood), matching the plain-name pair.
- **Source-linked same-grade candidates:** `The Groove` 8638/86751, `The Swim` 57847/87010, `Black Monday` 30784/115546, `Megalopolis` 57887/128732, and `Times Square` 36953/58135. Each has only one linked ID. Retain that link, or transfer it if a different canonical ID is chosen.
- **Hold despite name match:** `Ring Toss` 10156/89708 differs by three boulder grade steps; `Shingles Stand` 10578/56626 differs by two. OpenBeta has a V5 `Ring Toss` under review and a V4+ `Shingles Stand Start` under review; [Mountain Project lists Ring Toss as V5](https://www.mountainproject.com/area/105835116/white-pine-boulders) and [Shingles Stand Start separately from Shingles](https://www.mountainproject.com/area/106668641/tiger-stripe-boulder). Their grade disagreement needs a start/crag check. `Bates Problem` 7362/84720 differs by one; OpenBeta links 7362 to `Bates Problem (stand)` while it represents `Bates Problem (Sit)` separately as climb 241214. Keep the sit distinct. Generic names (`Mantle`, `The Roof`, `Right Side`, `Solo`, `Mystery`, `Unknown`, `Unnamed`) should never merge from the group key alone, especially in broad areas.
- **Large clusters:** `Moses` at Little Babylon has four original IDs, all grade 21; `Jugular`, `Hercules`, `International Turkey Patrol`, and `Solitude` there each have three. The repeated same-name cluster suggests duplicated source ingestion, but check whether the broad Little Babylon area covers distinct walls before collapsing all IDs.

No pair among the 213 has one record explicitly named `sit` and the other `stand` because they are exact-name groups. That does **not** prove identical starts: generic naming and omitted suffixes can conceal a variation. In the inspected Little Cottonwood/Castle Rock examples, separately named sit routes coexist with plain-name duplicates; preserve those separate route IDs.

## Guarded cleanup

1. Regenerate the 213-group inventory against **current production** and require each candidate to still have the same IDs, names, type, area, grades, send counts, and source links. Start with the 96 strongest same-grade/name-unique candidates, then the nine logged groups after dependency inspection. Do not bulk merge all 213.
2. For each candidate, confirm route identity and start using the most specific crag or boulder, source name/path and grade, and nearby distinct-start names. Exclude `unnamed`/`unknown`; hold generic names and grade gaps of two or more until individually checked.
3. Choose survivor by real user history first, then attached source identity, then stable oldest ID. Inspect production `sends`, `journal_entries`, and linked OpenBeta UUIDs for both IDs. Use the application's guarded `applyClimbMerge`/moderation path for logged routes; it handles unique-user send collisions, journal references, and source-link transfer. Avoid a raw `DELETE` or blind foreign-key update.
4. Apply a small reviewed batch, with expected-row guards and a saved ID mapping. Verify every old send/journal/source UUID now resolves to the survivor, `PRAGMA foreign_key_check` is empty, and counts/aggregates match. Retain the mapping for old climb URL redirects or at least auditability. Repeat only after spot checks.
