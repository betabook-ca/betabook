# OpenBeta catalog import + fuzzy/LLM dedupe for areas and climbs

## Context

Betabook's production catalog (10,237 areas, 141,199 climbs as of the dump this pipeline was built and validated against) has a real structural problem: area id 18, "Uncategorized," alone holds roughly 10,000 areas that were never placed into a real country/region hierarchy, and it already contains internal near-duplicates (e.g. "Millennium" and "Millenium" both parented there). OpenBeta publishes a much larger public dataset with a real geographic hierarchy and, per route, GPS coordinates. Folding it in serves two goals: it gives Betabook coordinates it doesn't have today, and it's the occasion to also resolve pre-existing internal duplicates against a canonical external reference.

Because OpenBeta's routes vastly outnumber Betabook's own and dedup requires comparing against the full existing catalog plus LLM arbitration for ties, this runs as an offline script — not a Worker request (no Queues/cron/Durable Objects/R2/KV exist to stage or schedule it, and Workers have CPU/wall-clock limits) — that fully automates matching, writes a durable audit trail, and persists an external-ID crosswalk so a _future_ re-sync only needs cheap key lookups instead of re-matching everything.

## Confirmed OpenBeta schema

The default `OpenBeta/parquet-exporter` export (github.com/OpenBeta/parquet-exporter, `schema.sql`) is a **single flat table**, one row per route — not separate area/climb files as originally assumed before this was checked. Its columns: `climb_id`, `climb_name`, `grade_yds`/`grade_vscale`/`grade_french`, `is_sport`/`is_trad`/`is_boulder`/`is_alpine`/`is_top_rope`, `country`/`state_province`/`region`/`area`/`crag` (a denormalized location breadcrumb), `latitude`/`longitude`, plus route metadata not currently mapped (`length_meters`, `bolts_count`, `first_ascent`, `safety`, `description`). There is no area-entity uuid graph in this export — `breadcrumbs.ts` synthesizes area nodes from the breadcrumb text columns instead (see its own comment for why the synthesized `externalId` is stable across runs). `schema.sql` is user-customizable, so `parquet.ts`'s `FIELD_CANDIDATES` tables try several plausible column names per field and `inspectParquetSchema` exists to check a new file's real columns before trusting a mapping.

## Design

- **Schema**: `latitude`/`longitude` on `areas`/`climbs`; `catalog_external_refs` (the crosswalk — unique on `(source, external_id)`); `catalog_import_decisions` (the audit trail, one row per decision, keyed by `run_id`).
- **`area_merge`**: mirrors the existing `climb_merge` moderation action (`actions/moderation-apply.ts`) — reparent children, delete the source, no send/journal collision handling to reproduce (areas don't have that). Climb-level Betabook-internal duplicates are deliberately _not_ auto-merged this way — `applyClimbMerge`'s collision handling is load-bearing and already tested there; hand-duplicating it as raw SQL risks getting it wrong against real user history.
- **Pipeline** (`scripts/openbeta-import/`): parse the parquet file (`parquet.ts`) → synthesize areas from breadcrumbs (`breadcrumbs.ts`) → load a local D1 snapshot for fast in-memory matching (`snapshot.ts`) → resolve areas top-down, country-level first (`run.ts`'s `resolveAreas`, using `match-areas.ts`'s exact/loose/fuzzy narrowing plus GPS-proximity tie-breaking) → resolve climbs within their resolved parent area (`resolveClimbs`, using `match-climbs.ts`) → detect Betabook-internal duplicate areas independent of OpenBeta entirely (`internal-duplicates.ts`, the actual fix for the Uncategorized-style mess) → render everything as plain SQL (`apply.ts`) rather than writing to remote D1 directly.
- **Depth-mismatch fallback**: OpenBeta's breadcrumb is a fixed 5 levels (`country/state_province/region/area/crag`); Betabook's real tree isn't that shape (confirmed empirically — under "United States," descendants cluster mostly at relative depth 2-3, not uniformly 1-4). `resolveAreas` first tries an OpenBeta level's direct children under its already-resolved parent (highest precision, since structural adjacency is a real signal); only when that comes up empty-handed does it fall back to `snapshot.ts`'s `descendantsOf` — the nearest matched ancestor's _entire_ subtree — via `matchArea`'s exact/loose tiers only (`{ allowFuzzy: false }`). The fuzzy tier is deliberately excluded from this wide fallback: a real run surfaced Jaro-Winkler's prefix bonus fuzzy-matching OpenBeta's "Okanagan" region grouping to Betabook's unrelated "Okanagan Falls" crag once the search widened past true siblings, which then mis-anchored (and lost matches under) that entire subtree. Fuzzy matching stays enabled for the narrow, structurally-adjacent tier, where that risk is much smaller. `resolveClimbs` mirrors the same fallback: a route's exact resolved crag area may itself not exist in Betabook even when a broader ancestor does, so a narrow-search "create" also widens to every climb under the nearest matched ancestor's subtree (again exact/loose only) before giving up — this alone raised climb matches roughly 4x in the same real run.
- **On "most Betabook data should match OpenBeta"**: worth stating plainly since it's a natural expectation and was checked, not assumed. Two ceiling measurements against the real snapshot: (1) ignoring hierarchy entirely, only 22.4% of unique OpenBeta climb names and 10.3% of unique area/breadcrumb names exact-fold-match _something_ in Betabook at all; (2) of climbs this pipeline still creates, 29.8% coincidentally name-match something _somewhere_ in Betabook, but that figure is inflated by generic route names (e.g. "Warm Up") recurring at unrelated crags worldwide — matching on name alone without area-scoping would produce wrong merges, which is exactly why the pipeline scopes to a resolved area in the first place. Both point to real, structural non-overlap between the two catalogs rather than a residual matching bug, so majority-level overlap isn't a realistic target without loosening matching in ways that trade correctness for coverage.
- **Country-name aliasing**: Betabook nests countries two levels deep (continent → country), while OpenBeta's breadcrumb has no continent level — a root-level OpenBeta row is a country and must be blocked against Betabook's country-level areas, never its true roots (the continents). Confirmed empirically: without this, matching produced zero results at all, since every OpenBeta country was being compared against continent names. Separately, `country-aliases.ts` bridges genuine spelling-convention differences (OpenBeta's "USA" vs Betabook's "United States", "Vietnam" vs "Viet Nam", etc.) that plain fuzzy matching correctly does not treat as near-duplicates — these are documented, hand-verified fixes for mismatches actually observed in a real run, not a general ISO-3166 table.
- **LLM arbitration** (`llm-arbitrate.ts`): one Claude call per still-ambiguous row, structured output only (Zod schema via `client.messages.parse`), never free text. Below the confidence threshold (including any `UNCERTAIN`), defaults to `CREATE_NEW` — a missed duplicate is cheap to fix later via `area_merge`/`climb_merge`; a wrong merge is not. `ResolvedAreaDecision`/`ResolvedClimbDecision`'s "create" variant carries an optional `arbitration` field so a create that followed real candidates (as opposed to the "no candidates at all" path) still records _why_ it wasn't matched — the audit trail's most important case. When no `ANTHROPIC_API_KEY` is available (`run.ts`'s `main`), `arbitrateOrOfflineDefault` skips the network call entirely and records the same `CREATE_NEW` default with a reason explaining why — an extension of the same policy, not a separate one, and what makes the pipeline fully automatable even without live API access. `resolveArbitration` also rejects a `MATCH` naming a `candidateId` outside the offered list (falls back to `CREATE_NEW` the same way a low-confidence one does), and the prompt itself wraps every untrusted catalog field (name/location/grade/discipline) in delimited, explicitly-labeled tags so it reads as data, not instructions.
- **Ancestry-compatible wide-fallback matching**: the depth-mismatch fallback above (and its climb equivalent) searches a large, structurally-uncorrelated subtree once the narrow direct-children/direct-area search comes up empty — `allowFuzzy: false` rules out one class of false positive there (see "Okanagan"/"Okanagan Falls" above), but an _exact_ name collision between two unrelated real places deep in the same subtree is still possible without a second check. `resolveAreas`/`resolveClimbs` cap a wide-fallback candidate's own extra depth beyond the matched anchor at the count of the OpenBeta row's own remaining (not-yet-consumed) breadcrumb tokens — a candidate deeper than that can't plausibly correspond to the row's shallower remaining path, so it's excluded. A name-overlap requirement between intermediate ancestor levels was considered and dropped: OpenBeta's breadcrumb and Betabook's real tree often use different names for an equivalent structural level (e.g. OpenBeta's "Okanagan" region grouping vs. Betabook's "Kelowna" — a legitimate match this exact fallback exists to find), so requiring name overlap there would reject the very matches it's meant to catch. The depth cap alone is the safety check; `resolveByName`'s existing "more than one exact match is ambiguous, never guessed" rule remains the residual guard against a coincidental same-name collision within an otherwise depth-compatible subtree. For performance, each anchor's candidate subtree is indexed once by depth-beyond-anchor (`AncestryDepthIndex`, cached per anchor id) rather than re-scanned per OpenBeta row — the naive per-row filter was measured at 27+ minutes of CPU time on the real dataset without finishing and was replaced by this indexed approach.
- **Generated SQL correctness**: two bugs found by reading the pipeline's own output closely, both fixed in `apply.ts`. First, the audit row (`catalog_import_decisions`) for a "create" decision resolved its `betabook_id` via a second `last_insert_rowid()` call — but SQLite's `last_insert_rowid()` reflects only the single most recent insert on the connection, and by that third statement the most recent insert was the crosswalk row (a different table, its own autoincrement id), not the area/climb — every create's audit `betabook_id` was silently wrong. Fixed via a crosswalk subquery instead (the same pattern `parentIdSubquery` already used). Second, `chunkStatements` split raw lines into files without regard to which statements belonged to the same decision — since each output file is applied as a _separate_ `wrangler d1 execute` batch, a decision's entity-insert and crosswalk-insert landing in different files would break the `last_insert_rowid()` dependency between them. `renderAreaDecisions`/`renderClimbDecisions`/`renderAreaMerges` now return statement groups, and `chunkStatements` never splits one across a chunk boundary. `renderAreaMerges` (and `applyAreaMerge` itself, `actions/moderation-apply.ts`) also now retarget the source area's `catalog_external_refs` rows onto the target before deleting it, so a merge doesn't orphan an already-linked external row.

## Deployment: code vs. data

Two separate pushes. **Code** (schema migration, `area_merge`, the pipeline module itself) is ordinary git work — a migration is structural only, carries no bulk data, and CI applies it like any other. **Data** (the actual OpenBeta-derived rows) is generated as plain SQL and committed to the branch under `scripts/openbeta-import/output/<runId>/`, deliberately _not_ under `drizzle/migrations/` — that directory replays on every `db:migrate:local` and every Workers-project test run, so bulk data living there would wreck test runtime and pollute every local/test database. Applying the generated files to remote D1 (`wrangler d1 execute betabook-db --remote --file=...`, one file at a time, in order) is a separate, later, manual step — this pipeline never writes to remote D1 itself.

## A real run

Run `057c6ac0-615c-4007-ae7e-df47a0a712ff` (see `scripts/openbeta-import/output/057c6ac0-615c-4007-ae7e-df47a0a712ff/manifest.json`) was generated against the real OpenBeta parquet release (`v2026-09-13`, 231,924 routes) and the production dump provided at this feature's outset (10,237 areas, 141,199 climbs), after the CodeRabbit-review fix round described throughout "Design" above (audit-row correctness, chunk-safety, Unicode name folding, arbitration hardening, and — the change with the biggest effect on these numbers — the ancestry-compatible depth cap on wide-fallback matching): 1,398 areas matched, 18,708 created; 26,867 climbs matched, 195,796 created, 9,261 skipped (no Betabook-supported discipline); 146 Betabook-internal duplicate areas found, with merge SQL generated (`144_area_merges.sql`). Matched counts are intentionally lower than the pre-fix-round run's — the depth cap rejects some wide-fallback candidates the old, uncapped search would have accepted, trading a small amount of coverage for ruling out exact-name collisions in unrelated branches of the same subtree. This supersedes the run previously referenced here (`7a67f603-db8d-4660-a25e-a30c3cf67b20`, 1,322/24,741 areas/climbs matched) and, before that, two earlier runs found to severely undercount matches — `781b7cfb-c487-4726-a59c-8e10a177b854` (443/1,366 areas/climbs matched, the original breadcrumb-depth cascade bug) and an intermediate, never-committed run that added the area-level fallback but also surfaced the "Okanagan"/"Okanagan Falls" false positive before the climb-level fallback was added — see "Depth-mismatch fallback" above for both fixes. A broad sample of the resulting matches (areas and climbs, across multiple countries, including the original "Kelowna"/"Okanagan" motivating example) was manually checked against the real snapshot and confirmed correct, both for the deep match still succeeding and for depth-incompatible candidates being correctly excluded. Ambiguous cases after deterministic matching were all resolved via `arbitrateOrOfflineDefault`'s recorded-reason `CREATE_NEW` default (see "LLM arbitration" above), since no `ANTHROPIC_API_KEY` was available in the session that ran this; each case's reasoning is in `catalog_import_decisions`. That data has **not** been applied to any database — the generated SQL is for review.

## Non-goals

This is the one-time-repeatable offline pipeline plus the crosswalk table that makes a _future_ resync cheap (`(source, external_id)` lookups skip already-linked rows) — it does not build a live in-app "resync from OpenBeta" admin feature, a scheduled sync, or a review UI, and no CI workflow runs the backfill automatically.
